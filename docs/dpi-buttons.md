# Physical DPI-button mappings

Stop handling, enable **Buttons → Remap DPI buttons**, assign **DPI Up** and **DPI Down** on the first Buttons page, then Start. Original Naga Pro USB cable (`1532:008f`) and receiver (`1532:0090`) are supported. Bluetooth and other Naga models, including HyperSpeed, are excluded. The Cursor hardware-DPI slider remains separate. Record while stopped cannot detect DPI controls which emit no keyboard report under their original hardware assignment; select those inputs by name.

Only live normal-layer slots **11 (Down)** and **12 (Up)** are assigned temporary single-key F14/F13 reports. The raw reader decodes these as logical inputs 113/112, with the same press-time mapping, held shortcuts, modifiers and chords as other buttons. Normal keyboards and other mice are excluded. Side-button calibration using F13/F14 blocks enabling this feature. Stop or normal Quit restores the privately journaled original blocks. Writes, active onboard profile and readback are verified. A possibly landed write is included in rollback, and an outside assignment is preserved during recovery. Stored profile banks, profile selection, DPI values and side-panel assignments are not written by this controller.

## Evidence and scope

The earlier 0.4.3/0.4.4 implementation incorrectly addressed scroll-wheel slots 9/10; the earlier physical-DPI claim is withdrawn. 0.4.5 disabled it. New upstream evidence at [OpenSnek ff4a0e8641a96b2539553a21bed6b63c7e801f31](https://github.com/gh123man/OpenSnek/blob/ff4a0e8641a96b2539553a21bed6b63c7e801f31/CHANGELOG.md) explicitly validates original-Naga DPI slots 11/12 and includes them in its writable table. This is original TailorMouse Swift using the documented framing; no proprietary app is patched.

A separate bounded runtime trial on 2026-10-20 backed up the connected receiver’s actual slots 11/12, wrote/read back F14/F13 only in bank 0, then automatically restored and verified both original blocks. Fresh read-only queries confirm wheel slots 9/10 still contain original Scroll Up/Down blocks and hardware DPI remains 3200/3200. Raw evidence stays ignored under `.local/evidence/naga-dpi-*20261020*`; these are native diagnostic observations, not SteerMouse REA findings. The capture window received no isolated physical DPI hold test, so physical press/hold/release acceptance remains pending.

## Recovery and migration

Reconnect the same device at its original USB location and select the same onboard profile. While stopped, use **Buttons → DPI setup… → Restore Button Assignments** after a crash/unplug. The private durable journal in Application Support/TailorMouse/DPI Button Recovery is retained if identity, profile or current ownership cannot be verified. Never delete an unresolved journal. A new opted-in Start first recovers an existing matched journal. The legacy 9/10 journals remain recoverable, but new leases cannot target wheel slots and writes of the old wheel tunnel blocks are rejected.

The new opt-in uses `remapPhysicalNagaDPIButtons`. An old `remapNagaDPIButtons` flag is ignored, preserving the explicit opt-in boundary. Profile actions remain intact. Tests cover both transport scopes, migration, matched held aliases, backup ordering, landed-write rollback, external-change preservation, invalid/mixed slot rejection and legacy recovery. Builds, tests and isolated renders never write mouse settings or enable handling.
