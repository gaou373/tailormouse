# Physical DPI-button remapping

Version 0.4.3 adds **DPI Up** and **DPI Down** to the first Buttons page and to the Chords input menu. These are the two physical top controls, separate from Cursor's existing hardware-DPI slider and presets. Their actions belong to application profiles and use the same modifier selectors, held shortcuts and repeated anchor chords as other inputs.

While stopped, enable **Remap DPI buttons**, assign actions, then explicitly press Start. This opt-in applies to the original Naga Pro over wired USB (`1532:008f`) or its receiver (`1532:0090`). It defaults off when loading existing settings. Bluetooth (`1532:0092`) and other Naga models are excluded. Unassigned DPI inputs do nothing while this mode is running. Explicit Passthrough forwards the temporary F13/F14 key, rather than invoking the original hardware function.

## Live assignment lease

The app reads and privately journals the two original effective normal-layer function blocks, then maps slots `0x09`/`0x0a` to single keyboard usages F13/F14. Each write is verified by readback. Bank 0 is the only write destination; stored banks, profile selection, DPI values and side-panel assignments are not written. USB and receiver aliases are confined to positively identified Naga input connections; normal keyboard F13/F14 are unaffected. An existing side-panel calibration that uses either alias blocks enabling this mode rather than reinterpreting that button. Repeated HID snapshots produce no extra presses. Logical inputs 112/113 remain distinct from side buttons 100–111 and mouse clicks 0–31.

Stop before switching connections. Stop, normal Quit, permission/tap failure and startup failure release held output and restore live button blocks for connected mice. A partial or possibly landed write is included in rollback. Restoration compares each current block with its journaled original or TailorMouse's target before writing, preserving an outside change. Product, USB location, available serial and active onboard profile must match. A changed profile stops remapping rather than writing into the newly selected profile. The hardware-DPI and button controllers share a serial vendor-command queue.

Unplugging or crashing can leave a recovery record. Reconnect the same device at its original USB location and select the same onboard profile, then choose **Buttons → DPI setup… → Restore DPI Buttons** while stopped. A subsequent opted-in Start also recovers the matching journal before preparing the device again. Ambiguous, malformed or mismatched records are retained and reported, rather than overwritten or adopted. A forced termination cannot guarantee an immediate hardware restore. If recovery fails, keep the private recovery file in Application Support/TailorMouse/DPI Button Recovery.

Chord DPI inputs can be selected from the menu. The read-only Record control does not program DPI buttons while stopped; it cannot identify controls which emit no input under their original assignment.

## Evidence and validation

This is original TailorMouse code based on the public USB button-function framing documented by [OpenSnek](https://github.com/gh123man/OpenSnek/blob/1af99c711035842e2896cd2d0b666b41dc022a1d/docs/protocol/USB_PROTOCOL.md). No new SteerMouse binary analysis was performed and no target executable or assets are included.

On 2026-10-17 the connected receiver exposed five interfaces. The first native read-only input capture delivered only mouse-interface reports and no distinct DPI-button transitions. GET queries found effective slots 9/10 containing `01 01 09 00 00 00 00` and `01 01 0a 00 00 00 00`. A separate bounded runtime diagnostic privately backed up those blocks, wrote only bank 0 to F13/F14, verified both readbacks, and observed both usages during the user's physical DPI-button test. It then restored and verified both original blocks. Native-tool evidence remains ignored under `.local/evidence/naga-dpi-*20261017*` and `.local/backups/`; these captures are not REA target findings. The capture's filter omitted neutral reports, so it does not prove physical hold duration or a matched release. Physical hold/release and action acceptance in the installed build remain pending.

Tests exercise strict packet scope and response echoes, private-backup ordering, landed-write rollback, failed and partial recovery, external-change preservation, opt-in migration, exact transport aliases, repeated raw snapshots, simultaneous DPI holds, reset cleanup, and repeated button/scroll chords. Builds, unit tests and isolated UI renders never write device settings or activate handling.
