# Physical DPI-button mappings

Stop handling, enable **Buttons → Remap DPI buttons**, assign **DPI Up** and **DPI Down** on the first Buttons page, then Start. Original Naga Pro USB cable (`1532:008f`) and receiver (`1532:0090`), and the Naga V2 HyperSpeed receiver (`1532:00b4`), are supported. Bluetooth and other Naga models are excluded. The Cursor hardware-DPI slider remains separate. Record while stopped cannot detect DPI controls which emit no keyboard report under their original hardware assignment; select those inputs by name.

Only live normal-layer slots **11 (Up)** and **12 (Down)** are assigned temporary single-key F19/F20 reports. The raw reader decodes these as logical inputs 112/113, with the same press-time mapping, held shortcuts, modifiers and chords as other buttons. Normal keyboards and other mice are excluded. Side-button calibration using F19/F20 blocks enabling this feature. Stop or normal Quit restores the privately journaled original blocks. Writes, active onboard profile and readback are verified. A possibly landed write is included in rollback, and an outside assignment is preserved during recovery. Stored profile banks, profile selection, DPI values and side-panel assignments are not written by this controller.

## Evidence and scope

The earlier 0.4.3/0.4.4 implementation incorrectly addressed scroll-wheel slots 9/10; the earlier physical-DPI claim is withdrawn. 0.4.5 disabled it. New upstream evidence at [OpenSnek ff4a0e8641a96b2539553a21bed6b63c7e801f31](https://github.com/gh123man/OpenSnek/blob/ff4a0e8641a96b2539553a21bed6b63c7e801f31/CHANGELOG.md) explicitly validates original-Naga DPI slots 11/12 and includes them in its writable table. This is original TailorMouse Swift using the documented framing; no proprietary app is patched.

A separate bounded runtime trial on 2026-10-20 backed up the connected receiver’s actual slots 11/12, wrote/read back F14/F13 only in bank 0, then automatically restored and verified both original blocks. Fresh read-only queries confirm wheel slots 9/10 still contain original Scroll Up/Down blocks and hardware DPI remains 3200/3200. Raw evidence stays ignored under `.local/evidence/naga-dpi-*20261020*`; these are native diagnostic observations, not SteerMouse REA findings. The bounded capture received no isolated physical DPI holds. A separate installed-app trial reached ready with a journal containing only slots 12/11; Stop restored both original blocks and cleared the journal, independently confirmed by GET reads. Application profiles, side calibration, shared tracking and the wired reference remained equal to the pre-install backup. The option was returned to off. Physical press/hold/release acceptance remains pending.

## Recovery and migration

Reconnect the same device at its original USB location and select the same onboard profile. While stopped, use **Buttons → DPI setup… → Restore Button Assignments** after a crash/unplug. The private durable journal in Application Support/TailorMouse/DPI Button Recovery is retained if identity, profile or current ownership cannot be verified. Never delete an unresolved journal. A new opted-in Start first recovers an existing matched journal. The legacy 9/10 journals remain recoverable, but new leases cannot target wheel slots and writes of the old wheel tunnel blocks are rejected.

The new opt-in uses `remapPhysicalNagaDPIButtons`. An old `remapNagaDPIButtons` flag is ignored, preserving the explicit opt-in boundary. Profile actions remain intact. Tests cover both transport scopes, migration, matched held aliases, backup ordering, landed-write rollback, external-change preservation, invalid/mixed slot rejection and legacy recovery. Builds, tests and isolated renders never write mouse settings or enable handling.


0.4.7 reverses the physical direction assignment following the user’s 2026-10-21 report that the 0.4.6 mappings were flipped. Logical IDs 112/113 and saved actions remain unchanged. New recovery journals record the direction version; absent versions are treated as 0.4.6. Recovery recognizes only the temporary blocks belonging to that journal version before applying the new direction, preserving unrelated changes. An old tunnel without its original journal is rejected rather than adopted. Matched hold/release, distinct actions and prior-direction recovery are regression tested.

0.4.8 replaces internal F13/F14 signals with F19/F20 to avoid F14 display-brightness shortcuts. Raw HID decoding and scoped Quartz consumption recognize the new signals only while opted in. Recovery retains the exact original blocks and distinguishes version 1 (0.4.6), version 2 (0.4.7), and version 3 (F19/F20); it never adopts an unjournaled temporary assignment. Logical buttons and saved actions are unchanged. Regression checks cover held down/up edges, repeated snapshots, disconnect release and recovery for each version. On 2026-10-21 receiver recovery restored both original slots and removed its journal, independently verified by GET; the user confirmed that unplugging/reconnecting the stopped receiver cleared the lingering brightness repetition. Physical acceptance on 0.4.8 remains pending.

A read-only session-event capture while stopped recorded 240 autorepeated F14 key-down events (key code 107, OS source PID 0) and no matching release during its 20-second window. The receiver emitted no new raw reports during a separate idle window. Together with the user-confirmed reconnect recovery, this supports a lingering OS F14 hold rather than a TailorMouse action-repeat loop. Captures stay in ignored `.local/evidence/`.

## Naga V2 HyperSpeed (0.4.9)

Read-only GET queries on 2026-10-20 against the user's receiver (`1532:00b4`, firmware 1.1, 90-byte feature interface, transaction ID `0x1f`) returned the same framing as the original Naga. Live slots 11/12 hold the factory DPI blocks `06 01 01` (stage up) and `06 01 02` (stage down); wheel slots 9/10 and buttons 1–3 also answer, so the slot table matches. The device-mode query returns normal mode `00 00`, but the active-profile query (`05 84`) is rejected with status 3.

A bounded trial wrote the F19 block to slot 11 only, read it back exactly, restored `06 01 01` and confirmed it by GET. Evidence: ignored `.local/evidence/hyperspeed-dpi-slot11-trial-20261020.txt`. No other slot, stored profile or DPI value was written.

The HyperSpeed therefore uses the existing transaction, journal and recovery. Because it reports no onboard profile, its liveness check is the device-mode query (status 4 means the receiver's mouse is off, as for the Naga Pro receiver) and the journal records profile 1. Its raw keyboard reader already decodes F19/F20 from both receiver interfaces. Physical press/hold/release acceptance on 0.4.9 remains a user check.
