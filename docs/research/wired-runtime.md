## Observed

The user reported TailorMouse running, ordinary clicks appearing in activity, side button 1 producing alert sounds without activity, and four USB device rows. Wired vendor/product `0x1532:0x008f` has four HID endpoints at one USB location (`1122608`). Two expose keyboard collections, one exposes the mouse, and one exposes an auxiliary collection. Endpoint IDs `4296098172`–`4296098175` share the physical USB device ancestor `4296098157`. Therefore the four rows are interfaces, not four attached mice.

During the requested side-1 probe, Quartz delivered keycode 18 down/up/repeats with sender field 87 equal to `4296084967`. That sender resolves to `AppleHIDKeyboardEventDriver` under **Karabiner DriverKit VirtualHIDKeyboard 1.8.0**, rather than any Naga endpoint. TailorMouse's exact-sender guard correctly declined to attribute those keys to the mouse. Karabiner's [privacy documentation](https://karabiner-elements.pqrs.org/docs/privacy/) describes exclusive keyboard capture; its [device configuration](https://karabiner-elements.pqrs.org/docs/manual/configuration/configure-devices/) supports selecting which devices it modifies.

The active Karabiner profile was changed only to ignore original Naga device variants for wired, receiver and Bluetooth identities. Normal keyboard rules and other device settings were preserved. The original configuration was backed up under ignored `.local/backups/`. Karabiner remained running. The user then confirmed side-button activity resumed.

A second capture, with TailorMouse closed, requested physical buttons 10, 11 and 12 once each with pauses. It observed complete keycode pairs in order: `29`, `36`, `18`, `36`, `24`, all with Naga keyboard sender `4296098195`. The initial interpretation incorrectly split the macros into separate buttons. A subsequent timestamped capture, while the user pressed buttons 10 and 11, consistently showed `29` + `36` and `18` + `36`. Return began about 160–175 ms after the prefix key-down. Therefore the corrected calibration groups button 10 as `0` + Return, button 11 as `1` + Return, and button 12 as the standard `=` key. The installed 0.2.1 decoder's 120 ms timeout split these actual macros. These are observations of this mouse's current assignments, not universal Naga defaults.

After fresh permission approval, the user confirmed all buttons responded without alert sounds, but reported incorrect input for 10 and 11. The timestamped capture and a failing regression test reproduced that remaining error.

A follow-up user-reported issue in 0.2.2 showed “Mouse button 1” before the correctly labeled release. The user then held 10 and 11 separately for three seconds without pressing the main buttons. The Naga-only capture included native left-click events for the first time. Each keyboard macro was immediately preceded by two complete left clicks from Naga mouse sender `4296098190`: four transitions spanning about 0.4 ms for button 10 and 5.4 ms for button 11. The keyboard macro completed in approximately 0.25 seconds despite the reported longer physical hold. Earlier keyboard-only captures missed these clicks. Attribution to the Naga endpoints is observed; the exact firmware/driver origin of this combined report is not established.

The user's saved TailorMouse default profile had no explicit side-button bindings. Version 0.2.0 treated these as Passthrough. Unhandled key input can trigger the macOS alert through the [responder chain](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/EventOverview/EventArchitecture/EventArchitecture.html). This explains the reported sound; no audio recording or sound-system suppression was performed.

## Original implementation changes

- Physical connection grouping merges interface rows, while exact interface sender lookup remains separate and rejects zero, unknown and ambiguous senders.
- Missing Naga mappings now use No action; explicit Passthrough retains original key behavior. Ordinary mouse clicks remain native.
- A transport calibration maps USB `0` + Return to side 10 and `1` + Return to side 11; the standard `=` mapping remains side 12. Actions and application profiles remain shared across transports. Calibration was written only to TailorMouse's separate settings after backing up the original.
- Sequence decoding defers its prefix for up to 250 ms, captures the initial profile/modifiers, emits matched logical transitions, and preserves original native transitions for Passthrough. Holding the prefix resolves as side 1; it cannot complete the macro before the prefix is released. Reset, Stop and disconnect drop pending state. An orphan release passes through.
- Version 0.2.3 recognizes the calibrated down/up/down/up left-click prelude followed by the corresponding keyboard prefix on the same physical connection. It buffers left-click candidates for up to 12 ms; unmatched clicks retain their order and original profile, and drag events flush pending clicks. Completed side-button actions consume the whole macro; explicit Passthrough retains both clicks and keys. A missing/incorrect keyboard suffix replays the prelude as ordinary input rather than silently dropping it. Stop/disconnect/recovery discard undelivered state.
- Persistent last-side-button press and release rows avoid overwriting an unreadably brief press with its release or subsequent ordinary mouse clicks. They report macro transitions, not true physical hold state.
- Local `runtime-status.json` stores the latest running status, connection count, aggregate mouse/Naga button down/up counts and the two most recent side-button transition labels. It contains no typed characters or general keyboard history.

### Raw-HID physical-hold check

A subsequent Naga-only probe opened all four wired endpoints with shared access (`IOHIDDeviceOpen` options 0), registered input-report callbacks, and closed them after 60 seconds. Existing input-listen permission was checked; no permissions were requested, interfaces seized, output/feature reports sent, or settings changed. The user held side 1, then 10 and 11 separately, releasing between them.

Keyboard endpoint `4296098173` emitted 16 eight-byte input reports. Usage `0x1e` (1) remained present for several seconds during ordinary side-1 holds; the final such pair lasted 4.36 seconds. Side 10 emitted usage `0x27` (0) followed by `0x28` (Return), ending 256 ms after its first keyboard report. Side 11 emitted `0x1e` (1) followed by `0x28` (Return), ending 256 ms after its first keyboard report. Each was preceded by the already identified left-click burst. No distinct physical-release report appeared when those side buttons were released later. The second keyboard endpoint and auxiliary endpoint emitted no input reports during this capture.

Mouse endpoint `4296098175` emitted 6,283 eight-byte reports. Descriptor inspection locates two vendor-page bytes before wheel and 16-bit X/Y. Across every captured report, those vendor bytes exactly equal the signed 8-bit clipped X/Y movement values; they are not a hidden side-button state in this capture. Its five ordinary button bits showed the brief left-click bursts and normal main clicks, without a held 10/11 state.

**Inference:** in the current onboard profile and report mode, neither Quartz nor the observed normal HID input reports supplies physical holds for these two macros. TailorMouse cannot derive their actual release time from this stream. Other proprietary report modes or vendor feature protocols are untested; their availability must not be inferred from callback silence. Changing the onboard assignments to distinct single keyboard functions, or selecting an existing profile with such assignments, is the next supported route to verify true holds. Razer's [Naga Pro guide](https://dl.razerzone.com/master-guides/RazerSynapse3/NAGAPRO-00000143-en.pdf) documents stored onboard profiles and keyboard-function assignments. Standard calibration should be restored only after the resulting reports are confirmed.

After the user reported returning from the Windows setup, a fresh shared-access capture on new USB endpoint IDs (`4296113693`–`4296113696`) still showed the old `0` + Return and `1` + Return macros with the preceding left-click bursts. No keyboard usage `0x2d` (minus) appeared. Selecting TailorMouse's standard-layout control removed its software calibration and reproduced the side-1 label and extra clicks; that control does not change onboard mouse assignments. The working USB macro calibration was restored, preserving other settings and the installed 0.2.3 binary. It remained present after reopening stopped. True holds remain unresolved until the active onboard profile exposes single-key down/up reports; future standard-layout changes must follow that confirmation.

Native metadata discovery confirms one grouped wired Naga connection containing four endpoints. The other three catalog rows are an internal trackpad, a drawing tablet and a gaming keyboard's pointing collection, not duplicate Naga devices.

Sequence recognition relies on current onboard assignments, not a firmware-provided physical button number. A Naga-attributed single prefix followed by Return within the window is indistinguishable from its macro. Physical buttons sharing a native key can also be ambiguous when used simultaneously. Distinct standard onboard keys avoid that ambiguity; the UI's standard-layout control removes calibration after hardware assignments change. No firmware or onboard profile was rewritten.
