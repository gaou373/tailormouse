## Observed

The user reported TailorMouse running, ordinary clicks appearing in activity, side button 1 producing alert sounds without activity, and four USB device rows. Wired vendor/product `0x1532:0x008f` has four HID endpoints at one USB location (`1122608`). Two expose keyboard collections, one exposes the mouse, and one exposes an auxiliary collection. Endpoint IDs `4296098172`–`4296098175` share the physical USB device ancestor `4296098157`. Therefore the four rows are interfaces, not four attached mice.

During the requested side-1 probe, Quartz delivered keycode 18 down/up/repeats with sender field 87 equal to `4296084967`. That sender resolves to `AppleHIDKeyboardEventDriver` under **Karabiner DriverKit VirtualHIDKeyboard 1.8.0**, rather than any Naga endpoint. TailorMouse's exact-sender guard correctly declined to attribute those keys to the mouse. Karabiner's [privacy documentation](https://karabiner-elements.pqrs.org/docs/privacy/) describes exclusive keyboard capture; its [device configuration](https://karabiner-elements.pqrs.org/docs/manual/configuration/configure-devices/) supports selecting which devices it modifies.

The active Karabiner profile was changed only to ignore original Naga device variants for wired, receiver and Bluetooth identities. Normal keyboard rules and other device settings were preserved. The original configuration was backed up under ignored `.local/backups/`. Karabiner remained running. The user then confirmed side-button activity resumed.

A second capture, with TailorMouse closed, requested physical buttons 10, 11 and 12 once each with pauses. It observed complete keycode pairs in order: `29`, `36`, `18`, `36`, `24`, all with Naga keyboard sender `4296098195`. The initial interpretation incorrectly split the macros into separate buttons. A subsequent timestamped capture, while the user pressed buttons 10 and 11, consistently showed `29` + `36` and `18` + `36`. Return began about 160–175 ms after the prefix key-down. Therefore the corrected calibration groups button 10 as `0` + Return, button 11 as `1` + Return, and button 12 as the standard `=` key. The installed 0.2.1 decoder's 120 ms timeout split these actual macros. These are observations of this mouse's current assignments, not universal Naga defaults.

After fresh permission approval, the user confirmed all buttons responded without alert sounds, but reported incorrect input for 10 and 11. The timestamped capture and a failing regression test reproduced that remaining error.

The user's saved TailorMouse default profile had no explicit side-button bindings. Version 0.2.0 treated these as Passthrough. Unhandled key input can trigger the macOS alert through the [responder chain](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/EventOverview/EventArchitecture/EventArchitecture.html). This explains the reported sound; no audio recording or sound-system suppression was performed.

## Original implementation changes

- Physical connection grouping merges interface rows, while exact interface sender lookup remains separate and rejects zero, unknown and ambiguous senders.
- Missing Naga mappings now use No action; explicit Passthrough retains original key behavior. Ordinary mouse clicks remain native.
- A transport calibration maps USB `0` + Return to side 10 and `1` + Return to side 11; the standard `=` mapping remains side 12. Actions and application profiles remain shared across transports. Calibration was written only to TailorMouse's separate settings after backing up the original.
- Sequence decoding defers its prefix for up to 250 ms, captures the initial profile/modifiers, emits matched logical transitions, and preserves original native transitions for Passthrough. Holding the prefix resolves as side 1; it cannot complete the macro before the prefix is released. Reset, Stop and disconnect drop pending state. An orphan release passes through.
- Local `runtime-status.json` stores the latest running status, connection count and aggregate logical Naga button down/up counts. It contains no typed characters or general keyboard history.

## Validation and limits

The first 0.2.1 installation hit a separate permission identity problem. Its designated requirement was a build-specific `cdhash`; no reusable signing identity was available. Native `tccd` logs explicitly reported a failure to match TailorMouse's existing code requirement for `kTCCServiceListenEvent`. This matches Apple's [ad hoc identity description](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements). The final build limits the native Accessibility prompt to once per launch and explains replacing stale entries. Targeted Accessibility and ListenEvent resets succeeded for `dev.tailormouse.app` only; neither the app nor installer grants permissions or performs automatic resets. The user subsequently confirmed the app was Running and side buttons no longer produced alerts. Updated-build approval and physical verification remain separate acceptance steps.

All 34 tests pass, including grouping four interfaces, separate physical mice, virtual/ambiguous source rejection, quiet side-button pairs, calibrated overrides and sequences, native macro replay, profile snapshots, repeats, timeouts, modifier changes, reset and source isolation. The new timing regression fails with the old 120 ms window and passes with 250 ms, verifying exactly one action and matched logical releases for both actual macros. Offline replay of the timestamped capture yields 35 side-10 down/up pairs, 28 side-11 down/up pairs, one standalone side-1 pair, no unrecognized events, and one action per press. This replay does not inject system input. Version 0.2.2 builds and installs successfully, passes strict signature verification, and opens with handling stopped. Installed executable SHA-256: `f96bb97bf95dd1b74479c35dcc56be8bf2d63dfd85989fe7d84acd4194e155bc`. Final physical verification of this build is pending.

Native metadata discovery confirms one grouped wired Naga connection containing four endpoints. The other three catalog rows are an internal trackpad, a drawing tablet and a gaming keyboard's pointing collection, not duplicate Naga devices.

Sequence recognition relies on current onboard assignments, not a firmware-provided physical button number. A Naga-attributed single prefix followed by Return within the window is indistinguishable from its macro. Physical buttons sharing a native key can also be ambiguous when used simultaneously. Distinct standard onboard keys avoid that ambiguity; the UI's standard-layout control removes calibration after hardware assignments change. No firmware or onboard profile was rewritten.
